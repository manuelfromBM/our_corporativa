Antes de subir
- El backend no está en git: backend/ tiene 0 archivos versionados, y Render despliega desde el repositorio. Hay que hacer commit primero. credenciales_equipo.txt ya está ignorado y los .db también.
- backend_go/: parece una copia antigua. Conviene no subirla, o borrarla si confirmas que ya no sirve.

Base de datos
- Disco persistente: agrega uno, por ejemplo montado en /var/data, y define DB_PATH=/var/data/team.db. Requiere un plan pago; el gratuito además se duerme sin tráfico.
- Limitaciones del disco: queda atado a una sola instancia, sin escalar a varias. Cada deploy tiene unos segundos de caída.
- Datos locales: tu base tiene 6 solicitudes y no se copian solas. El equipo y las migraciones sí se cargan al arrancar. Si esas 6 importan, o si editaste el equipo localmente, hay que subir el archivo team.db al disco.
- Alternativa: Turso u otra base gestionada evitaría el disco, pero implica cambiar el driver. Para este volumen, SQLite con disco alcanza.

Configuración del servicio
- Root Directory: backend
- Build: go build -o bin/server ./cmd/server && go build -o bin/crear-equipo ./cmd/crear-equipo
- Start: ./bin/server
- Health check: /api/team/slugs, porque no existe una ruta /health.
- Sin ajustes extra: el driver de SQLite es Go puro, así que no necesitas CGO, y el código ya lee el PORT que asigna Render.
- Versión de Go: go.mod pide 1.26.0; revisa en el primer build que Render la acepte.

Riesgos que conviene tener presentes
- El backend quedará público en una URL de Render, no solo accesible desde Next.js.
- POST /api/requerimientos no tiene sesión, y en lo que revisé no vi límite de envíos, así que podrían llenarte la base con spam. Se puede restringir con un secreto compartido entre Next.js y el backend.
